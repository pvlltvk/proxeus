## Highlights

**Exact aggregates over overlapping server_groups** (#27). The new `cross_group_exact_aggregates: true` (requires `cross_group_dedup`) declines aggregation pushdown while more than one `server_group` is configured, so the engine computes the aggregation locally over deduplicated raw series and `count(up)` finally matches `up`. Until now a series present in two groups was deduplicated on the raw path but double-counted under an aggregate, with no warning — exactly the migration case proxeus exists for. The trade is the point: raw series cross the network instead of a handful of per-group partials, which hurts most on wide ranges and high cardinality, and a query that used to fit under `--query.max-samples` as a few partials can now exceed it and fail outright. Recording and alerting rules run through the same engine, so their values and thresholds move with the flag and pay that cost every evaluation interval. The gate counts *configured* groups, not overlapping ones, so groups holding disjoint data pay for no correctness gain. Off by default; a single-group deployment is unaffected. The decision is visible as `proxeus_pushdown_nodes_total{result="fallback",reason="exact_aggregates"}`. See README "Cross-group dedup".

**Cross-group dedup runs natively over SeriesSets** (#13, #23). Dedup used to drain every backend `SeriesSet` into a `model.Matrix`, merge, and convert back — around 21% of allocations under load. It now buckets series by their reduced label set in ordinal order; the winning `storage.Series` is passed through untouched and losers are never iterated. Semantics are unchanged: lowest ordinal wins, winner label set kept, collision counting, first-appearance output order, single-backend pass-through, partial-response warnings. Benchmarked at 3 groups × 2000 series × 60 samples: ~17-21x fewer allocations and bytes, ~5-6x faster wall clock. The old `model.Value` implementation is deleted (#23), with randomized differential tests against it retained as a test-only oracle.

**Raw sample fetch from VictoriaMetrics via `/api/v1/export`** (#14). VictoriaMetrics has no `remote_read`, so VM groups fetched raw samples through `/api/v1/query` with a range selector — matrix JSON with every value a quoted string. The `victoriametrics:` dialect block gains `raw_fetch: export`, which decodes NDJSON from `/api/v1/export` with `reduce_mem_usage=1` on the raw fallback path only; `Query`, `QueryRange`, `Series` and the label endpoints are untouched. ~1.6-1.8x faster decode with 42% fewer allocations at 500 series × 100 samples. Default is `query`, so nothing changes until you ask for it; `raw_fetch: export` is mutually exclusive with `remote_read: true`, and the boundary-sample, latency-offset and duplicate-timestamp caveats are documented in the README.

**A production-grade Helm chart** (#20). The chart inherited from promxy did not pass `helm lint` at all, and several templates could never have applied — an HPA on `autoscaling/v2beta2` carrying an `autoscaling/v1`-only field, a PDB on `policy/v1beta1`, a VPA that emitted invalid YAML, and a default config using `kubernetes_sd_configs` with no RBAC to make it work. It now ships locked-down pod and container `securityContext` defaults matching the scratch image's uid 65534, a `terminationGracePeriodSeconds` derived from proxeus's own drain flags, `--storage.path` always backed by a volume, `extraSecretMounts` and `webConfig.existingSecret` for the `*_file` options, ServiceMonitor and PodMonitor gated on the operator CRDs, a `checksum/config` annotation so `helm upgrade` rolls on config change, `--web.enable-lifecycle` defaulted **off**, a `--check-config` init container, RBAC, NetworkPolicy, `values.schema.json`, and renders that refuse with an explanation for known footguns (MCP without authentication, a PVC with replicas and no `ReadWriteMany`, HPA alongside an actuating VPA). CI gained `.github/workflows/helm.yml`: `helm lint`, then `helm template` for defaults and every `ci/*-values.yaml` through `kubeconform -strict`. The chart is `0.2.0` with `appVersion: v0.3.0`, and `image.tag` defaults to the appVersion (#31). **The chart is not published to any repository and has never been applied to a cluster** — verification stops at lint plus schema validation, so treat a first real-cluster run as unexercised.

**The upstream PromQL suite runs again, and it found wrong answers** (#15, #18). `TestUpstreamEvaluations` globbed a `vendor/` path that stopped existing when the project de-vendored, so it had been passing in 0.00s with zero subtests. The fixture directory is now resolved from the module, an empty glob is a hard failure, and whole-file skips became per-eval exclusions that keep the rest of a file running. That immediately exposed three wrong-answer bugs in the `count_values` pushdown rewrite, all fixed here: `count_values((("v")), m)` panicked with an HTTP 500, `count_values("v", m offset 5m)` read its value from 10m ago, and `count_values without (instance) ("v", m)` dropped the very label the function exists to produce. Per-eval exclusions also let six fixtures that were skipped wholesale over the plain-HTTP config come back: **703 evals now run on that config that previously ran only on remote_read.** The sweep takes ~21m, so it sits behind `PROXEUS_UPSTREAM_PROMQL` with its own `make test-upstream` target and CI job; `make test` is unchanged.

**Prometheus fork at `v0.305.0-proxeus.4`** (#24). Proxeus has always set `LookbackDelta` on the selector it synthesizes for a pushed-down range query, and the fork's engine never read that field for sample lookup — it consulted it only when computing Select hints, while the per-step lookup used the engine-wide 5m default. The fork now threads the resolved delta through the selector evaluation path. The visible symptom was `count_values` in range mode, where each generated `{value="..."}` series lingered five minutes past the step that produced it.

## Behaviour changes

- **Downstream timeouts and cancellations are classified as such** (#21). `NormalizePromError` tested the error with a type assertion, which never matched because every fan-out error is already wrapped by the per-target and per-server-group `ErrorWrap` — so a backend answering `errorType: timeout` reached the client as `errorType: execution`. It now uses `errors.As` for both `*v1.Error` and `*promapi.ResponseError` and returns the downstream error paired with the promql error, so clients get the right `errorType` *and* keep the full message. Anything keyed on `errorType` — Grafana, retry logic, alerting — was reading `execution` for these before and will now see `timeout` or `canceled`.
- **Backend error messages no longer carry the internal target address** (#17). A query a backend rejected used to surface as `error in servergroup ord=0: error in target=http://10.0.3.7:9090: execution: ...`, handing an internal address to whoever typed the query. For downstream `bad_data` and `execution` errors the per-target frame now drops its message, leaving `error in servergroup ord=0: execution: ...`. The server-group frame stays on purpose: with mixed backends the groups genuinely disagree about which one objected. Timeouts, cancellations, `internal`, malformed responses and connection failures keep their full context on every path, target included, because there the target identity is what an operator needs. Related: a query rejected in partial-response mode now says the backend `rejected the query` instead of claiming a healthy backend was `unavailable`.
- **`histogram_fraction` over classic `_bucket` floats is no longer refused** (#22). It was listed in `histogramOnlyFuncs`, so its mere presence diverted a query to remote_read or, in strict mode, refused it — even though the fork's `funcHistogramFraction` has an explicit classic-histogram branch and the inputs were plain float series the JSON API carries exactly. This is the same trade `histogram_quantile` has always made: a native-histogram argument is no longer caught by function name alone and falls to the `isHistogramName` metadata signal, which needs `histogram_metadata_refresh`. 11 upstream evals recovered. One consequence to expect: because the query is no longer refused up front, it is now sent to the backends, so a backend that does not implement `histogram_fraction` at all — VictoriaMetrics does not — answers with its own error instead of proxeus's "configure remote_read". Restricting the query to a group that does implement it returns real values.
- **`avg` is pushed down unchanged when there is one server group** (#25). `avg` was rewritten to `sum()/count()` unconditionally, because per-group partials cannot be recombined without their weights. With a single group there are no partials, so `avg` now goes down as written and the backend's own incremental mean comes back. That fixes overflow at extreme magnitudes — `avg` over series at ±9.988e307 returned `+Inf`, `-Inf` or `0` depending on backend series order — and costs one downstream request per `avg` instead of two. Multi-group keeps the rewrite, and its overflow is untouched.
- **A histogram whose bucket layout drifts across a range now warns** (#26). Prometheus's JSON encoding lists only non-empty buckets, so an empty bucket takes its implied boundary with it and a series' custom-bucket layout can change from sample to sample; PromQL then treats the samples as incompatible and an aggregation over that range silently returns **no series at all**. `decodeMatrix` compares `CustomValues` across a series' histogram samples and attaches one PromQL warning on a mismatch, pointing at `remote_read` as the fix. The data is unchanged — this is a warning where there was silence, and it can show up in Grafana on affected queries.
- **Panic responses no longer contain a stack trace** (#16). `ApacheLoggingHandler.runHandler` put `debug.Stack()` into the error it returned and the caller wrote it into the 500 body: 7,221 bytes of absolute build paths and internal package layout, reachable from a valid PromQL query. The stack now goes to the log and the client gets `internal server error`.

## Fixes and internals

- `NodeReplacer` was 789 lines and is where every recent pushdown fix landed; it is now decomposed into `pkg/proxystorage/node_replacer.go` with one method per switch arm, guards in their original load-bearing order, and `proxy.go` a pure deletion (#29). Behaviour is bit-for-bit intact: pushdown decisions were diffed main-vs-branch over 69 query shapes × instant/range × 3 configs and came out identical.
- The pushdown decision contract is now pinned directly (#30): six tests assert the `proxeus_pushdown_nodes_total{node,result,reason}` delta *and* the downstream requests issued — query string, window, and whether the fan-out carried the aggregate-pushdown marker, which is what decides whether the cross-group merge dedups or unions. The file passes unchanged on the pre-refactor tree, so it pins shared behaviour rather than the new structure.
- `validateDialect` returned after the first matching dialect block, letting a stray second block through (#14).
- `MOTIVATION.md` claimed Grafana "will not add them together, and it will not let you alert on the sum". Server-side expressions do exactly that; both passages now make the real argument instead (#16).

## Breaking

- **`cross_group_partial_response: false` now actually fails the query** (#19). It is documented as the strict setting — every server group must answer — and it has never behaved that way: a group that errored was silently dropped and the query returned the remaining groups' data, with no warning and no error. `NewCrossGroupMultiAPI` relied on each group occupying its own fingerprint bucket via `APILabels.Key()`, which the `*servergroup.ServerGroup` actually passed in does not implement, so every group landed in the zero bucket and one success satisfied the requirement. Buckets are now assigned by position. **If you run with this setting and a backend is flaky, you will see errors where you used to see quietly incomplete data.** That is the documented contract; if you want the old behaviour, set `cross_group_partial_response: true`.
- **`--check-config` now rejects configs that startup rejects** (#28). It did not run `ProxeusConfig.Validate()`, so a config with, say, `cross_group_dedup_metadata: true` and no `cross_group_dedup` exited 0 from preflight and then fatally failed at startup. Validation moved into `ConfigFromBytes`, the one path every loader goes through, which also covers SIGHUP reloads — an invalid reload used to reach earlier reloadables before being refused. **A CI pipeline running `--check-config` over an invalid config will newly fail.** The success message also changed from `<file> if valid proxeus config file syntax` to `<file> is a valid proxeus config file`; nothing parses it, the Helm chart's init container only reads the exit code. Not yet covered: `validateUniqueServerGroupLabels`, which is still unexported in `pkg/proxystorage`.
- `pkg/promhttputil` loses two exported symbols, the `MergeValuesDeterministic` function and the `OrdinalValue` type, along with their unexported helpers (#23). Nothing in proxeus called them after #13; `DedupStats` stays. Relevant only if you import the module as a library.
