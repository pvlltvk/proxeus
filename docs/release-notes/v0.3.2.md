**Nothing in the binary changed.** No Go code outside tests was touched since v0.3.1, so the image behaves exactly as
v0.3.1 did — same flags, same config, same query results. The substance of this release is in the Helm chart, which now
refuses a configuration that silently duplicates recording-rule writes, and in how release notes get published. If you
do not deploy through the chart, there is nothing to do here.

## Helm chart

**`config.rule_files` with more than one possible replica is now refused** (#34). proxeus evaluates `rule_files`
in-process and has no leader election, so every replica evaluates every rule. Alerting rules are fine — Alertmanager
deduplicates by label set, the same as it does for a pair of HA Prometheus servers. Recording rules are not: each
replica `remote_write`s the same series, so the write target receives one copy per replica. The chart defaulted to one
replica but shipped an HPA scaling to 10, with no warning anywhere. `chart.validate` now fails the render when
`config.rule_files` is set **and** more than one replica is possible — `replicaCount > 1`, or `hpa.enabled` with
`hpa.maxReplicas > 1`. The escape hatch is `rules.alertingOnly: true`, which states that the rule files record nothing,
the same shape as `mcp.authenticatedByProxy`. **A rules deployment already running more than one replica will newly
fail to render**, which is the point — it was double-writing. Deliberately not checked when `configMap: <name>` supplies
the config: the chart cannot see inside a config it does not render, and a false failure on a working deployment is
worse than the footgun, so that case is documented rather than guarded.

**A "High availability" section in the README**, because the guard needed somewhere to send people. In-process rules are
the single-replica option. The recommended scale-out path is an external ruler that queries proxeus — Thanos Ruler
(`thanos rule --query=http://proxeus:8082`), or a rules-only Prometheus with `remote_read` against proxeus and
`read_recent: true`. The federated view survives the move, since the ruler's queries still go through proxeus, and it
needs no proxeus-side configuration beyond dropping `rule_files`. The chart README gains a "Rule evaluation and
replicas" section, and `ci/rules-values.yaml` covers a single-replica rules deployment in the existing `helm template` +
`kubeconform -strict` sweep. Chart version stays `0.2.0` with `appVersion: v0.3.0`, and the chart is still not published
to any repository nor applied to a real cluster — verification stops at rendering.

## Release process

**This body was published straight from the repository** (#35). `.github/workflows/release.yml` reads
`docs/release-notes/<tag>.md` out of the tagged tree and passes it as `--notes-file`; with no such file it falls back to
`--generate-notes` exactly as before and logs a workflow warning, so a quick patch tag still publishes rather than
failing the job. Every release before this one needed a `gh release edit <tag> --notes-file …` after the fact — the
public body was the raw commit list for a few minutes, and the notes themselves were never reviewable before going out
because they lived outside the repo. The one thing that is easy to get wrong is documented in
`docs/release-notes/README.md` and the CONTRIBUTING "Releasing" section: **the notes file has to be merged before the
tag is created**, since the workflow reads it from the tagged tree. `v0.3.0.md` and `v0.3.1.md` are in the repo too,
copied verbatim from the bodies those releases already carried.

## Tests

`allowed_groups` is covered through the `oidc` provider (#36). Group authorization had unit coverage only through the
`basic` and `trusted_header` providers, so the `groups_claim` path — including a `groups` claim that is a single string,
the Keycloak shape, and one with a non-string entry — ran untested. The new cases drive a policy with `allowed_users`,
`allowed_groups` and a route rule from the claims of a signed token, and were checked against a deliberately broken
implementation. The same policies were then watched working end-to-end against Dex and oauth2-proxy in the sandbox, on
both group-carrying providers; no bugs and no gap between the documented and the observed behaviour. Test-only, no
production code.
