**The Helm chart was installed on a real Kubernetes cluster for the first time, and two of its defaults were fatal.**
Rendering-only CI had signed off on both. The chart is the substance of this release: `config.proxeus.server_groups`
no longer defaults to discovering every pod in the cluster, and `webConfig.existingSecret` no longer crash-loops the
pod forever. **Both fixes are breaking for anyone relying on the old defaults** — see the upgrade notes below. The
binary also moves to a supported Go toolchain, since Go 1.25 reached end of life. **No Go source changed in this
release**; same flags, same config, same query results as v0.3.2.

## Helm chart

Chart version **0.2.0 → 0.3.0**, `appVersion` **v0.3.0 → v0.3.3** (#39). Minor bump rather than patch because the
chart is pre-1.0 and the default-config change breaks existing values files. A default install was also still pulling
the v0.3.0 image.

**The default config OOMKilled the pod on its first query.** `config.proxeus.server_groups` defaulted to an unfiltered
`kubernetes_sd_configs: - role: pod`, which made every pod in the cluster a PromQL backend — proxeus itself included.
One `/api/v1/query?query=up` took the pod from roughly 20 MB to 691 MB at 20s and 1828 MB at 60s, then OOMKilled it,
with the query still returning `context deadline exceeded`. Nothing static caught this: `helm install --wait` reported
success and the pod went Ready, and the failure only arrived with the first query. The default is now `server_groups:
[]` with a template-time guard that refuses to render and names the trap, so the chart asks for backends instead of
inventing them. Re-tested with namespace-scoped, port-filtered discovery against a real backend: **29,645 queries over
five minutes, memory flat at 38–40 MiB, 0 restarts**, returning data rather than timeouts. `deploy/k8s/proxeus.yaml`
carried the identical `role: pod` default on the raw-manifest path and was fixed the same way.

**`webConfig.existingSecret` meant permanent `CrashLoopBackOff`.** `--web.config.file` covers the whole listener —
`/-/healthy`, `/-/ready` and `/metrics` included — but both probes hardcoded `scheme: HTTP` and sent no credentials,
so the kubelet got a 401 and liveness restarted the pod forever. There is now a `probes:` block (`scheme`,
`httpHeaders`) used by both probes, `scheme`/`tlsConfig`/`basicAuth`/`authorization` passthrough for the monitors, and
`webConfig.tls` / `webConfig.basicAuthUsers` to declare what the Secret turns on, since the chart cannot read inside
it. The combinations that used to ship broken are now refused at render time with the reason. Both a basic-auth
release and a TLS-plus-basic-auth release stay Ready with 0 restarts and answer kubelet probes 200. The MCP guard no
longer accepts a bare `webConfig.existingSecret` as authentication — it used to recommend exactly the setup that
crash-loops.

**All 8 `ci/*-values.yaml` files now install and reach Ready**; three of them previously could not. They carry
explicit `server_groups`, `ci/persistence-values.yaml` drops a `storageClassName` that existed nowhere, and the files
that need Secrets or ConfigMaps created out of band now say so. `vpa.yaml` gained the same CRD capability guard the
two monitors already had instead of hard-failing, and NOTES warns when a monitor or the VPA is enabled while its CRDs
are absent, so a green install that created nothing is no longer silent. The README documents the required backends,
the `webConfig` probe caveat, and the values `helm upgrade` cannot change (`service.clusterIP`,
`storage.persistence.size`, `storage.persistence.storageClassName`) — each reproduced before being written down.

**Chart CI was reporting success on a failing render.** `helm template | kubeconform` ran without `pipefail`, so the
exit status came from kubeconform cheerfully validating zero resources while helm had already errored out. The Render
step now uses `shell: bash`, renders the defaults with a real backend configured, and asserts that the bare-defaults
case is refused rather than rendering it and hoping.

## Upgrade notes

**You must now set `config.proxeus.server_groups` explicitly**, or point the chart at an externally managed config
with `configMap: <name>`. A chart upgrade that relied on the old `role: pod` default will fail to render with a
message explaining why. That is deliberate: the previous behaviour installed cleanly and then died on the first query,
which is a worse outcome than a refused render. A scoped example is in the chart README.

If you set `webConfig.existingSecret`, you must also declare `webConfig.tls` and/or `webConfig.basicAuthUsers`, and
supply probe credentials through `probes.httpHeaders` (and `probes.scheme: HTTPS` for TLS). Renders that would
reproduce the crash loop are refused.

## Toolchain

**Go 1.25 reached end of life**, leaving go1.26.x and go1.27.x as the supported lines, so builds move to **Go 1.27.1**
(#38, #40). v0.3.2 shipped `go1.25.14`. The Dockerfile uses `golang:1.27-alpine` and all three CI pins use
`go-version: '1.27'`; both stay on the *floating* minor tag on purpose, so patch releases keep arriving without a
commit. Pinning an exact patch is precisely what left the base image stale and shipped a critical Go stdlib CVE in
v0.3.0.

The `go.mod` `go` directive is **1.27.1** (#40). #38 had set a 1.26.0 floor while building and testing with 1.27, and
nothing in CI ever exercised 1.26 — the compatibility window was an unverified promise. Rather than add a job to back
it, the floor now states what is actually built and tested. No `toolchain` directive is pinned. golangci-lint moves
from v2.7.2 to **v2.13.2**, because v2.7.2 cannot read Go 1.27 export data and fails with `export data version 4 is
greater than maximum supported version 2`.

## Dependencies

- `golang.org/x/crypto` v0.55.0 → **v0.56.0**, closing CVE-2026-78662, CVE-2026-56855 and GO-2026-5932. This was
  blocked until the Go floor moved: v0.56.0 requires go 1.26 or newer, which is why v0.3.1 stopped at v0.55.0.
- `go.opentelemetry.io/otel/sdk` v1.44.0 → **v1.45.0**, closing CVE-2026-81870, and pulling `otel`, `otel/metric` and
  `otel/trace` to v1.45.0 and `go-logr/logr` to v1.4.4.
- `google.golang.org/grpc` v1.84.0 → **v1.83.2**. This is a downgrade, deliberately. v1.84.0 is the newest stable
  release but shipped *without* the fix for CVE-2026-84445 (HIGH); the fix was backported to v1.82.2 and v1.83.2 and
  landed forward in the unreleased v1.85.0-dev, so the highest safe version available today is lower than the newest
  one. Nothing in the module graph requires above v1.80.0, so the constraint costs nothing. A comment in `go.mod`
  records why, to stop the next routine bump from walking back onto v1.84.0.

**The measurable security impact is smaller than that list suggests.** govulncheck against the shipped go1.25.14 image
already reported only 2 affecting vulnerabilities, and it reports the same 2 afterwards: `GO-2026-4887` and
`GO-2026-4883`, both Moby, both with no published fix. They reach us as `api/types/*` struct definitions pulled in by
Prometheus's `discovery/install` for Docker service discovery; no daemon code is ever run. What did improve is further
out: vulnerabilities in imported packages went 1 → 0, and in required modules 9 → 7. The real benefit of this release
is being back on a Go line that will keep receiving patches at all.
